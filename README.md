# Stepwise

Планировщик поступления для школьников из Казахстана и Центральной Азии.

## Проблема

Абитуриент в одиннадцатом классе не знает, что уже потеряно. Дедлайн подачи в
январе выглядит далёким, но регистрация на экзамен, который нужен для этой
подачи, закрывается в ноябре — и когда человек впервые открывает сайт вуза, он
уже опоздал, не сделав ничего неправильного.

Существующие сервисы отвечают на вопрос «куда поступать». Этот отвечает на три
других:

```
Какие пути ещё открыты?
Когда каждый перестанет быть достижимым физически?
Что сделать прямо сейчас, чтобы не потерять варианты?
```

## Решение

Единица продукта — **путь (дверь)** с точкой невозврата. Для каждой программы
движок строит цепочку обязательных шагов **назад от дедлайна подачи** и
вычисляет последний день, когда путь ещё можно собрать. Доска сортируется по
срочности, а не по рейтингу вуза.

Чего продукт **не делает** принципиально:

- не считает вероятность поступления и не показывает «шансы»;
- не придумывает даты: если данных не хватает, путь получает статус
  `needs_data`, а не правдоподобную дату;
- не конвертирует валюты без курса;
- не решает за человека, какой вуз «лучше».

## Стек

Next.js 16 (App Router) · React 19 · TypeScript (strict) · Tailwind 4 ·
Zustand + persist · Zod · Vitest · motion · Supabase (Auth + Postgres).

Движок остаётся полностью клиентским и детерминированным — Supabase не
пересчитывает ничего, только хранит вход/выход движка и разбирает, кто есть
кто. Подробности — в «Аутентификация и данные» ниже.

## Архитектура

```
Profile (Zustand, буфер в localStorage["stepwise-storage:<id>"])
   ↓
Match      — подходит ли путь: жёсткие ограничения отдельно, мягкий счёт отдельно
   ↓
Schedule   — обратное планирование от дедлайна → точка невозврата
   ↓
Door       — статус, дата, цепочка шагов, объяснение
   ↓
Route      — доска, отсортированная по срочности + сводка
   ├── Leverage     — что одно изменение профиля откроет
   ├── Diff         — что изменилось между двумя расчётами
   └── Next action  — ровно одно действие
   ↓
Zustand → persist → localStorage (кэш) ⇄ lib/state/remote-sync.ts → Supabase student_state (истина)
```

Движок ничего не знает про Supabase: он как принимал `Profile`, так и
принимает — откуда она взялась, локально или после синхронизации,
`computeRoute` не различает.

Движок (`lib/engine/`) — чистый TypeScript: ни сети, ни часов, ни React, ни
модели. `today` передаётся аргументом, поэтому сервер, браузер и тест дают один
и тот же результат. Данные каталога — статические типизированные модули в
`data/`.

| Модуль | Отвечает за |
|---|---|
| `lib/engine/schedule.ts` | обратное планирование, точка невозврата |
| `lib/engine/match.ts` | соответствие профилю, жёсткие ограничения |
| `lib/engine/route.ts` | сборка доски, сортировка, сводка |
| `lib/engine/leverage.ts` | перебор изменений профиля |
| `lib/engine/diff.ts` | сравнение двух досок |
| `lib/engine/next-action.ts` | выбор одного следующего шага |
| `lib/engine/questions.ts` | выбор следующего вопроса интервью |
| `lib/engine/profile-patch.ts` | применение изменения к профилю |
| `lib/state/app-store.ts` | всё состояние приложения |
| `lib/state/remote-sync.ts` | какая сторона (локальная/удалённая) новее, синхронизация с `student_state` |
| `lib/auth/route-guard.ts` | чистая функция редиректа: кто куда должен попасть |
| `supabase/migrations/0001_init.sql` | схема, RLS-политики, RPC — см. «Аутентификация и данные» |
| `lib/career/` | таксономия, скоринг, все три этапа, вето, кризис-детектор — см. «Найти профессию» |
| `supabase/migrations/0003_parent_career_signal.sql` | таблица голоса родителя, RLS — см. «Найти профессию» |

## Запуск

```bash
npm install
npm run dev          # http://localhost:3000
```

Вход, интервью после логина и родительский кабинет требуют настоящего
Supabase-проекта — без `.env.local` экраны `/start` и `/parent/join/[code]`
покажут ошибку подключения вместо формы. Настройка — в «Аутентификация и
данные» ниже. Всё остальное (движок, каталог, `/demo`) работает без Supabase
вообще.

Проверки:

```bash
npm run typecheck
npx vitest run
npx eslint
npm run build
```

Мобильная проверка в настоящем браузере (Chrome с машины, без загрузки
браузера в node_modules):

```bash
npm run build
npx next start -p 3123
node scripts/mobile-qa.mjs     # 360 / 390 / 430 px, скриншоты в public/qa
```

Скрипт падает, если появилось горизонтальное переполнение, если кнопка ниже
32px или если экран вообще не отрисовался.

## Сценарий проверки

```
/                     → лендинг
/start                → вход/регистрация: email и пароль
/interview            → пост-логин: свободный текст + 5–7 адаптивных вопросов
/diagnostics          → что известно, чего не знаем, правка любого поля
/doors                → доска путей по срочности, быстрая правка условий, leverage
/doors/[id]           → точка невозврата, что её определяет, цепочка шагов, источники
/compare              → два пути по осям решения
/roadmap              → шаги по месяцам, сколько путей держит каждый; «Пригласить родителя»
/next-action          → одно действие
/sources              → источники и методика
/profile              → аккаунт, кто привязан из родителей, выход
/parent/join/[code]   → регистрация/вход родителя по инвайт-коду от ученика
/parent/dashboard     → кабинет родителя, только чтение, переключатель детей
/demo                 → полноценный демо-режим на профиле Амира, без входа
/profession           → карьерное интервью: этап 1 → 2 → 3a/3b → результат
```

Ключевая демонстрация: на `/doors` изменить бюджет → доска пересчитывается на
устройстве мгновенно → открывается «Что изменилось» с тем, что открылось,
закрылось и как сдвинулся следующий шаг. Перезагрузка страницы сохраняет
профиль, доску и отмеченные шаги.

Полный путь целиком покрыт тестом `tests/judge-scenario.test.tsx`.

## Демо-режим

`/demo` — не витрина и не слайд-шоу: одна кнопка «Пройти демо за Амира»
отдаёт посетителю весь настоящий продукт, полностью заполненный и полностью
интерактивный, без регистрации. Профиль — Амир Ерболұлы, 16 лет, 11 класс,
Шымкент (`data/demo-profile.ts`), по сценарию «Путь пользователя: Амир из
Шымкента». Каждое число на каждом экране — реальный вывод `computeRoute`,
`computeLeverage`, `lib/career`'а и остального движка на этом профиле и на
настоящем каталоге, а не переписанный вручную текст: если движок посчитал
иначе, чем иллюстративный пример в документе, экран показывает то, что
посчитал движок.

**Изоляция — структурная, не по договорённости.** Демо-сессия — это cookie
`stepwise-demo`, синтетический статус `"demo"` в `useAuthStore`
(`lib/state/auth-store.ts`), и стор, посаженный на собственный ключ
`localStorage` (`stepwise-storage:demo`, `lib/state/demo-mode.ts`) — тем же
механизмом, что и обычный аккаунт (`lib/state/remote-sync.ts` делает то же
самое для `stepwise-storage:<id>`). Ни один файл в демо-пути ни разу не
вызывает `createClient()` из `@/lib/supabase/client` — физически нет кода,
которым демо-сессия могла бы прочитать или записать что-то в Supabase.
`proxy.ts` проверяет cookie раньше любого обращения к Supabase, поэтому демо
работает и без интернета до базы. Каждый заход через «Пройти демо» пересаживает
стор на чистые данные Амира заново — тинкеринг одного судьи не переживает
даже обновление страницы, не то что не протекает в чужую сессию.

Бейдж «Демо-режим» и кнопка «Выйти из демо» — в сайдбаре и в мобильном
хедере (`components/app-nav.tsx`), видны на каждом экране.

**Честная находка, а не сделанный по сценарию момент**: оверлей «Что
изменилось» (экран 11 документа) действительно работает — правка любого
поля в «Разбор» настоящая, пересчёт настоящий, оверлей открывается по
`view.pendingChange` тем же кодом, что и для реального студента. Прямая
проверка в браузере, впрочем, показала, что для текущего сочетания «профиль
Амира + нынешний каталог» смена бюджета/грант/переезд/уровня английского
через этот редактор не меняет набор открытых путей — а рычаг, который
`computeLeverage` считает работающим (подтвердить немецкий B1 → +3 пути),
при точно таком же изменении через живой редактор тоже не даёт разницы.
Это значит, что где-то между тем, как `computeLeverage` подставляет
изменение, и тем, как его реально применяет `editAnswer`, есть расхождение —
не выдумано и не подчищено под красивую цифру, а оставлено как честная
находка для отдельного разбора `lib/engine/leverage.ts` vs
`lib/engine/profile-patch.ts`. Механизм оверлея при этом рабочий: он
корректно показывает «набор путей и сроки остались прежними», когда это
правда, — то есть делает ровно то, что должен, даже когда результат не
самый эффектный.

## Аутентификация и данные

До этого раздела продукт не имел аккаунтов: «профиль» был именной коробкой в
`localStorage`, без пароля и без сервера, а «Экран для родителя» — анонимной
read-only ссылкой со снимком профиля прямо в URL. Оба решения были честными
компромиссами на своё время, но не выдерживали двух вещей, которые продукт
теперь обязан уметь: вернуться к своим ответам с другого устройства, и дать
родителю *свой* независимый вход, а не то, что предъявителю ссылки.

### Архитектура

Supabase Auth (email + пароль) поверх Postgres. Регистрация — минимальная:
email и имя. Личное интервью — класс, интересы, бюджет, языки — начинается
только после входа, на `/interview`,
и остаётся ровно тем же экраном (`AdaptiveInterviewScreen`,
`useAdaptiveInterview`), просто на другом месте в дереве роутов: было
`/start` до логина, стало `/interview` после.

```
sign up/in (Supabase Auth)
   ↓
public.users row создаётся триггером на auth.users, role: student | parent
   ↓
student:                              parent:
  /interview, если !onboarding_completed    /parent/join/[code] → создать/войти
  → /doors, /roadmap, …                     → /parent/dashboard (read-only)
```

### Схема (`supabase/migrations/*.sql`)

| Таблица | Смысл |
|---|---|
| `users` | зеркало `auth.users` для чтения через PostgREST: id, role, email, name, auth_provider, onboarding_completed |
| `parent_invites` | одноразовые коды приглашения, с TTL 7 дней; закрыта для прямого доступа — только через RPC |
| `parent_child_links` | кто кому родитель; PK `(parent_user_id, student_user_id)`, один родитель — много детей |
| `student_state` | `student_user_id`, `schema_version`, `state jsonb`, `updated_at` — вход/выход движка, версионировано |
| `parent_notes` (`0002_parent_notes.sql`) | короткая заметка от родителя ученику: `target_type` (`door`/`action`/`general`), `target_id`, `body` — см. «Родительский кабинет» |
| `parent_career_signal` (`0003_parent_career_signal.sql`) | голос родителя по части 9 карьерного интервью: три поля, PK `(parent_user_id, student_user_id)`, апсерт — см. «Найти профессию» |

Шесть RPC делают всю запись, которую нельзя доверить прямому `INSERT`/`UPDATE`
через RLS-политику: `create_parent_invite`, `get_invite_info` (единственная,
доступная анонимно — для экрана `/parent/join/[code]` до входа),
`redeem_parent_invite`, `revoke_parent_link`, `rename_self`,
`mark_onboarding_complete`. Роль (`student`/`parent`) выбирается прямо в
`signUp({options:{data:{role}}})` на клиенте — единственный способ создать
аккаунт здесь это email+пароль, поэтому роль известна уже в момент регистрации
и триггер `handle_new_user()` просто копирует её в `public.users`, без
отдельного шага «доопределить роль после входа».

**Гарантия, ради которой всё это написано:** у `student_state` есть
`SELECT`-политика, разрешающая родителю читать связанного ученика, и
`INSERT`/`UPDATE`-политики, упоминающие только `student_user_id = auth.uid()`.
Для роли «родитель» такой политики нет вообще — не скрыта в UI, а физически
отсутствует в базе. Прямой вызов REST API с JWT родителя на запись в
`student_state` получает `42501`/0 затронутых строк, см. чек-лист ниже.

### Настройка

1. Создать проект на [supabase.com](https://supabase.com) (или через
   `supabase projects create` из Supabase CLI).
2. Открыть SQL Editor → выполнить по очереди все файлы в `supabase/migrations/`
   по номерам (`0001_init.sql`, `0002_parent_notes.sql`,
   `0003_parent_career_signal.sql` — каждая следующая ссылается на таблицы из
   предыдущих). Через CLI то же самое — `supabase db push` после `supabase link`.
3. Скопировать Project URL и `anon public` ключ (Settings → API) в
   `.env.local`:

   ```bash
   NEXT_PUBLIC_SUPABASE_URL=
   NEXT_PUBLIC_SUPABASE_ANON_KEY=
   ```

Входа через Google в продукте нет — только email и пароль, поэтому
настраивать OAuth-провайдера и redirect URL для него не нужно.

### Перенос локального состояния

Кто пользовался продуктом до аккаунтов, ничего не теряет: `lib/state/
remote-sync.ts` при первом входе читает старый ключ `stepwise-storage`, и если
там есть настоящие ответы (а не пустой стор), поднимает их в `student_state`
этого аккаунта и удаляет старый ключ — чтобы вторая учётная запись в том же
браузере не могла забрать те же ответы себе. С этого момента у каждого
аккаунта свой ключ (`stepwise-storage:<id>`), так что выход и вход другим
пользователем в одном браузере не путает данные.

### Данные несовершеннолетних — что и почему

Продукт хранит: email, хэш пароля (полностью управляется Supabase Auth —
приложение никогда не видит и не хранит пароль в открытом виде), имя, и факт
связи родитель–ученик. Это минимум, без которого не работают ровно две вещи,
которые прямо просили: «вернуться на другом устройстве» и «у родителя
отдельный вход». Не хранится и не запрашивается ничего сверх этого — ни
телефон, ни адрес, ни документы, ни дата рождения. `student_state` хранит
готовый результат работы движка (профиль, доску, прогресс) — сервер ничего не
пересчитывает и не анализирует, только читает и пишет то, что посчитал
браузер.

### Найдено живым прогоном

Автоматических e2e-тестов против живого Supabase-проекта в репозитории нет —
их негде хранить credentials для CI — но сам прогон один раз реально
состоялся: проект поднят через Supabase CLI/Management API, обе миграции
применены, а весь чек-лист ниже пройден настоящим Chrome через Puppeteer
(регистрация → интервью → доска → план → инвайт → родитель → RLS), не только
руками и не только по коду. Три настоящих бага нашлись ровно на этом шаге —
ни `npm run check`, ни один из 299 тестов их не ловит, потому что все они
требуют реального Postgres/браузера одновременно:

1. **`useAuthSession` перерендеривал компонент бесконечно** — селектор
   `useAuthStore((state) => ({status, user}))` возвращал новый объект на
   каждый вызов, а `useSyncExternalStore` (на нём построен хук Zustand)
   считает это «состояние изменилось» и рендерит снова, снова получая новый
   объект — React падал с «Maximum update depth exceeded» на `/interview`
   сразу после первого ответа. В jsdom-тестах компонент рендерится один раз и
   не успевает войти в цикл, поэтому баг был невидим до реального браузера.
   Правка — обернуть селектор в `useShallow` (`features/auth/use-auth-session.ts`).
2. **`gen_random_bytes` не резолвился** в `generate_invite_code()` — Supabase
   по умолчанию ставит `pgcrypto` в схему `extensions`, а не `public`, и
   `create extension if not exists pgcrypto` в миграции успевает молча создать
   расширение без единого сигнала о том, в какую схему оно легло. Правка —
   схема-квалифицированный вызов `extensions.gen_random_bytes(8)`.
3. **Неоднозначная ссылка на колонку `code`** в `create_parent_invite()` —
   `returns table (code text, ...)` неявно объявляет `code` переменной
   PL/pgSQL внутри тела функции, и `where code = v_code` стало нечитаемым и
   для Postgres тоже: он не мог понять, колонка это таблицы или переменная.
   Правка — `where parent_invites.code = v_code`.
4. (Не баг флоу, но нашёлся тем же способом) **Удаление аккаунта родителя,
   который хоть раз погасил инвайт, падало** — у `parent_invites.used_by_parent_id`
   не было `on delete` вообще, поэтому удаление `auth.users`-записи родителя
   упиралось в внешний ключ. Правка — `on delete set null`: инвайт остаётся
   записанным как использованный, просто без ссылки на удалённого родителя.

Итог живого прогона: студенческий путь регистрация → интервью → доска (61 из
75 путей) → план (1 из 10 шагов сделано) — работает; родительский путь
инвайт → своя регистрация → `/parent/dashboard` с ровно теми же цифрами —
работает; прямая попытка родителя записать в `student_state` и адресовать
заметку не связанному с ним ученику — обе отклонены на уровне RLS (`403`/`0`
строк), проверено настоящим bearer-токеном через `curl`, а не только через UI.

### Ручная проверка (чек-лист)

Юнит-тестами покрыта вся чистая логика (`lib/auth/route-guard.test.ts`,
`lib/auth/auth-errors.test.ts`, `lib/state/remote-sync.test.ts`); всё, что
требует реального Auth/Postgres, стоит перепроверять руками по этому списку
после любого изменения схемы или экранов входа — тем же способом, что описан
выше:

- [ ] Регистрация email+паролем → редирект на `/interview` (или «проверь
      почту», если включено подтверждение email).
- [ ] Повторная регистрация тем же email → понятная ошибка, не 500-ка.

## Оформление

Лендинг заморожен вместе с `app/globals.css`, поэтому палитра приложения живёт
в `styles/app-theme.css` и действует только внутри `.stepwise-app`. Tailwind
резолвит `bg-card` в `var(--card)` в месте использования, так что переопределения
подхватываются всеми существующими утилитами — ни один класс в компонентах
менять не пришлось, а главная страница рендерится ровно тем же CSS, что и раньше.

**Продукт чёрно-белый.** Приложение — это то же ночное небо, что и лендинг:
тот же чёрный, те же серые чернила, звёздное поле под контентом
(`.stepwise-app::before`, три слоя градиентных точек, ноль запросов). Тема
стартует тёмной независимо от системной настройки — переключатель в рельсе
остался, но белое приложение сразу после чёрной главной читалось как другой
продукт.

Шкала срочности была цветовой (мята / янтарь / коралл) и стала яркостной:

| Статус | На чёрном | Почему так |
|---|---|---|
| закрыт | тусклый серый | прошедшее время, намеренно спокойное |
| открыт | средний серый | срочности нет |
| закрывается | светлый | пора |
| последний шанс | вывернутая плашка: белый фон, чёрный текст | горит |

Смысл не потерялся, сменился носитель: на чёрном внимание собирает свет. Побочно
шкала стала различимой при любой форме дальтонизма, чего про пару «мята/янтарь»
сказать было нельзя. Статус нигде не держится на одном оттенке — рядом стоит
слово и цветная кромка строки (`.lane-*`). В светлой теме всё зеркально: чем
ближе к закрытию, тем темнее.

На `/doors` сводка: счётчики, кольцо и шкала «когда закрываются» по месяцам. Всё
из `route.summary` и самих дверей — ни одного числа, написанного в разметке.
Процентов на экранах нет намеренно: «81 %» рядом со словом «открыто» читается
как шанс поступления, а такого числа в продукте не существует.

## Данные и источники

Каталог настоящий: **75 вузов в 19 странах, 85 источников, 10 действий**. Он
собирается детерминированным импортом из `data/raw/universities_verified.json`:

```bash
node scripts/import-universities.mjs              # → data/catalog.generated.ts
node scripts/import-universities.mjs --explain mit  # как прочитан один вуз
```

Сырой файл лежит в репозитории, поэтому любую дату на экране можно проследить
до предложения, которое опубликовал вуз. Импорт — единственное место между
ними, и он намеренно скучный.

### Карта и картинки вузов

Секция охвата на лендинге — настоящая карта, а не диаграмма. Береговые линии —
Natural Earth 1:110m, запечённые в SVG-пути один раз:

```bash
npm run map      # data/raw/countries-110m.json → data/world-map.generated.ts
```

Ни библиотеки карт, ни тайл-сервера, ни ключа: секция рендерится на сервере,
работает без сети и не может «не загрузиться» на глазах у посетителя. Проекция —
равнопромежуточная цилиндрическая, ровно потому, что её формула из двух
умножений применяется дважды (к берегам в генераторе и к вузам в браузере) и обе
копии заведомо одинаковы. Координаты кампусов — `data/campuses.ts`, единственная
таблица в продукте, написанная руками и без провенанса: она решает, где нарисована
точка, и никогда — что сказано в дате. Булавка — город, размер — сколько путей,
плашка называет все вузы в нём поимённо.

Фотографий вузов у нас нет, и выдумывать их продукт, который обещает показывать
только то, что может подтвердить, не станет. Поэтому у каждого университета своё
**небо** — `components/university-crest.tsx`: сцена, детерминированно выведенная
из названия. Одно имя — одно небо, всегда, на любом устройстве, без единого
сохранённого байта и без запроса. Это не фотография кампуса, и подпись под
картинкой так и говорит. Когда появится настоящий снимок с автором и лицензией,
он кладётся в `public/universities/` и прописывается в
`data/university-photos.ts` — небо для этого вуза исчезает сразу везде: в
карточке, на карте и на странице пути.

`tests/map-integrity.test.ts` следит за тем, что таблица координат не сгнила:
у каждой программы есть координата, лишних нет, и вузы одного города лежат в
пределах 60 км друг от друга — это ловит перепутанный знак и переставленную пару.

Сложность в том, что сроки опубликованы прозой: «Early Action — 1 ноября
(решение в середине декабря). Regular Action — 4 января. Тесты: до 30 ноября
для EA, до 31 декабря для RA. Финпомощь: 30 ноября (EA), 15 февраля (RA)».
Три правила делают это разбираемым без догадок:

1. **Считается только подача.** Дата решения, экзамена, взноса, досылки
   документов или подтверждения места — не срок закрытия пути, хотя в тексте
   она почти всегда стоит позже.
2. **Путь закрывается на последнем раунде подачи.** Ранний раунд — это
   возможность; продукт отвечает на вопрос, когда возможности не станет.
3. **Год берётся из текста** или выводится по циклу поступления (месяцы с
   августа — год до набора, остальные — год набора). Выведенный год помечается
   `derived`, а не `verified`: год наш, а не вуза.

Четыре уровня доверия — и каталог честно неоднородный:

| Уровень | Сколько | Что означает |
|---|---|---|
| `verified` | 23 | вуз назвал дату целиком, вместе с годом |
| `derived` | 38 | день и месяц из источника, год выведен по циклу |
| `last_cycle` | 8 | опубликован календарь прошлого цикла; новый вуз не объявил |
| без даты | 6 | срок прочитать нельзя → `needs_data`, а не догадка |

Шесть вузов остались без даты намеренно: четверо из них прямо пишут, что единой
даты нет. Экран показывает их формулировку и ссылку.

Источник без URL — это честное состояние, а не недоделка: ссылка появляется
тогда, когда человек реально открыл страницу. Придуманный URL хуже
отсутствующего, потому что выглядит проверенным.

`tests/data-integrity.test.ts` проверяет каждую запись каталога: уникальность
id, реальность дат, существование источника, ссылочную целостность цепочек
действий и то, что `verified` не появляется без URL и даты проверки. Отдельный
тест закрепляет дюжину дат, на которых парсер когда-то ошибался — регрессия
разбора не видна глазом: продукт всё так же показывает уверенную дату, просто
неправильную.

## AI

AI живёт **только на границах системы** и ничего не считает. Провайдер —
Google Gemini, вызывается напрямую через `fetch` в `lib/ai/boundary.ts`
(без SDK — весь код провайдера в одном файле, JSON-режим ответа задаётся
`responseMimeType`). Маршруты:

```
POST /api/parse                 свободный текст → поля профиля (+ противоречия, + уровни уверенности)
POST /api/explain                рассчитанные факты о двери → 2–3 предложения
POST /api/diff                    рассчитанный diff → формулировка «что изменилось»
POST /api/career-extract-axes     свободный ответ карьерного интервью → сдвиги по осям (см. «Найти профессию»)
POST /api/career-next-question    выбор id вопроса из банка этапа 2
POST /api/career-freeform         свободное интервью этапа 3b
```

Что модель **не делает** — структурно, а не по инструкции: в схемах ответа
просто нет полей для даты, срока, счёта, количества путей и вероятности. Она
получает уже посчитанный результат и возвращает слова.

**Grounding.** Каждое число и каждая дата в сгенерированном тексте сверяются с
входными фактами (`lib/ai/grounding.ts`). Не сошлось — ответ выбрасывается и
показывается детерминированный шаблон. Проценты запрещены всегда: в продукте
нет ни одной величины в процентах, поэтому «%» в ответе означает выдуманную
меру. Поле `grounded` отражает результат проверки, а не намерение.

**Ретраи.** Невалидный JSON или ответ не по схеме — ровно одна повторная
попытка со строгой инструкцией и текстом ошибки. Второй промах — шаблон.
Операционные сбои (нет ключа, таймаут, 429, 5xx) не ретраятся вообще:
детерминированный ответ мгновенный и всегда доступен.

**Кэш.** Ответы кэшируются в `localStorage` по хэшу запроса
(`lib/api/ai.ts`). Кэш хранит только формулировки — двери, даты и счётчики
пересчитываются движком на каждый рендер и никогда не читаются из кэша.

**Ключ.** Читается только на сервере (`lib/ai/client.ts` с `server-only`).
`NEXT_PUBLIC_`-варианта нет, `.env.local` в `.gitignore`. Включить локально:
положить `GEMINI_API_KEY` в `.env.local` (получить на
[aistudio.google.com/app/apikey](https://aistudio.google.com/app/apikey));
`GEMINI_MODEL` — необязательный оверрайд модели, по умолчанию
`gemini-3.6-flash`, с отключённым «thinking» (`thinkingBudget: 0` в
`lib/ai/boundary.ts`) — без этого модель тратит токены бюджета на
невидимые рассуждения и обрезает JSON-ответ на середине, что подтверждено
прямым запросом к API перед тем, как это было исправлено.

**Без ключа продукт работает полностью.** Деградирует только язык: интервью
разбирает текст правилами, объяснения берутся из шаблонов. Это покрыто тестами
(`tests/ai-routes.test.ts`) и проверено в браузере на запущенном сервере без
ключа.

## Родительский кабинет

Родитель получает свой собственный вход — не ссылку — и видит план ребёнка
только для чтения, посчитанный тем же движком заново на сегодняшний день, а
не замороженным снимком. Инвайт-коды и RLS-гарантия — в «Аутентификация и
данные» выше; здесь — что именно показывает `/parent/dashboard`
(`features/parent/parent-dashboard.tsx`) и откуда берётся каждое число.

**Одна вычислительная логика на двоих.** Ни один счётчик на этом экране не
пересчитан заново «на глаз»: `computeProgress`/`reachableActionIds`
(`features/route/use-progress.ts`) — та же функция, что считает процент
выполнения на `/roadmap` у самого ученика, вызывается родительским экраном
напрямую на данных из `student_state`. Так же переиспользованы
`computeRoute`, `computeNextBestAction`, `getActiveDoors` из `lib/engine`
(не изменены) и формулировка «что значит закрытая дверь»
(`CLOSED_DOOR_MEANING`, `features/route/ui.tsx`) — дословно та же, что на
`/doors/[id]`. Это не совпадение, которое может разойтись при следующей
правке: это один и тот же вызов.

Что видит родитель на `/parent/dashboard`:

1. **Профориентация** — ведущее направление и до двух соседних, каждое с
   цитатой из собственных ответов ребёнка и честной строкой «что тяжело» (тот
   же рендер, что на `/profession`), плюс форма из трёх вопросов части 9
   контентного пакета («Что думаете вы») и — если родитель её заполнил и
   результат у ребёнка уже есть — блок «Стоит обсудить дома»: во что метит
   родитель против того, что реально следует из ответов ребёнка, без вердикта,
   кто прав. См. «Найти профессию».
2. **Прогресс** — открыто/закрывается/закрыто/нет данных по путям, и
   сделано/в работе/запланировано/не начато по обязательным шагам плана.
3. **Ближайший дедлайн** — что за шаг, почему именно он (та же формулировка,
   что на `/next-action`), и что произойдёт с конкретными путями, если его не
   сделать вовремя — не абстрактное «риск», а названные университеты и то же
   объяснение «закрыт ≠ поступить нельзя», что видит ребёнок на странице пути.
4. **Деньги и программы** (`features/parent/programs-table.tsx`) — таблица по
   открытым путям (вуз, страна, финансирование, стоимость) и сводка сверху:
   сколько полностью финансируются, и диапазон цены — отдельно по каждой
   валюте, никогда не смешанный (продукт не конвертирует валюту без курса, и
   сводка не станет первым местом, где он это сделает).
5. **Бейджи доверия** — `ConfidenceBadge` везде, где есть дата или цена, так
   что оценка по прошлому циклу никогда не выглядит как подтверждённый факт.
6. **Заметка ученику** (`features/parent/parent-notes-panel.tsx`,
   `parent_notes` — единственная таблица, где родитель имеет право что-то
   написать) — короткий текст, привязанный к конкретному открытому пути,
   конкретному шагу плана, или общий. Ученик видит её в контексте: на
   `/doors/[id]` (заметка к пути), на `/next-action` (к шагу) или на
   `/profile` (общая) — компонент `features/notes/notes-from-parent.tsx`.
7. **Переключатель детей** — реальный, не заглушка: несколько связанных
   учеников дают вкладки над кабинетом, каждая — свой полный кабинет.

### Что родитель не может (и почему)

- **Изменить что-либо в данных ученика.** У `student_state` нет
  `INSERT`/`UPDATE`-политики для роли «родитель» — не скрытая кнопка, а
  отсутствующее разрешение в базе. Прямой вызов REST API с JWT родителя
  ничего не меняет, см. чек-лист выше.
- **Отредактировать или удалить заметку задним числом от имени ученика.** У
  `parent_notes` нет `INSERT`-политики для ученика вообще — писать в эту
  таблицу умеет только связанный родитель, отвечать некому.
- **Увидеть данные не связанного с ним ученика.** Каждая политика (`users`,
  `parent_child_links`, `student_state`, `parent_notes`) проверяет
  существование строки в `parent_child_links` для этой конкретной пары —
  угадать чужой `student_user_id` в запросе недостаточно.
- **Пересчитать что-то по-своему.** Кабинет не содержит собственной копии
  движка — только вызовы `lib/engine/*`, которые ученик тоже вызывает; у
  родителя физически нет пути получить другой ответ на тот же вопрос.

## Найти профессию

Полная реализация «Career Interview Content Package» — документа, переданного
как единственный источник истины для этой фичи. Каждый идентификатор, вес,
формулировка вопроса и системный промпт ниже дословно транскрибированы из
документа; единственные места, где инженеру пришлось самому что-то решить
(численная шкала для качественных профилей полей, формула сходства, синтез
строки «что тяжело» там, где в таблицах нет готового текста), явно помечены
комментарием в коде — см. `lib/career/fields.ts` и `lib/career/results.ts`.

```
/diagnostics, боковая панель → «Найти профессию»
/profession → этап 1 (10 вопросов) → этап 2 (адаптивно, одно поле) →
              [этап 3a (расширение) → этап 3b (свободное интервью)] → результат
```

### Таксономия и данные (`lib/career/`)

16-мерный вектор черт — 6 фасетов `O_*` (0–100) и 10 биполярных осей `A_*`
(−100…+100), `lib/career/types.ts`. 11 широких полей с профилями
(`fields.ts`) и матрицей соседства (часть 7.3). Все ~120 узких специализаций
из частей 3.1–3.11 — `lib/career/specializations/*.ts`, один файл на поле,
каждая строка таблицы документа перенесена как есть (локальные оси хранятся
буквально — стрелкой или названием категории, а не насильно проведены к одной
числовой шкале, которую документ не задаёт). Карта жёсткого вето из Q10 —
`aversions.ts`, помечена в самом документе как «расширяемая инженером».

### Этап 1 — `lib/career/stage1.ts` + `scoring.ts`

Десять вопросов части 4 дословно: форматы, порядок вариантов, веса сдвигов,
запасная формулировка Q1 при пустом ответе, вето третьего варианта Q7
(`TRD_PILOT`, `MED_SURG`, весь `SEC`…) — тот же механизм, что у Q10. Скоринг
(`scoring.ts`) — чистые функции: сборка вектора, нормализация с клампом по
диапазонам документа, сходство со профилем поля (нормализованное расстояние
по измерениям, которые профиль поля вообще называет), отбор кандидатов в
пределах 15% от лидера, уверенность как относительный отрыв. Полностью
детерминировано — ни одного обращения к сети.

### Этап 2 — `lib/career/stage2.ts` + `stage2-banks/*.ts`

Все 11 банков части 6.2 (~100 вопросов) перенесены дословно, со структурными
тегами «кого разделяет» (`groupA`/`groupB`), а не только текстом. Офлайн-
селектор (`pickNextStage2Question`) реализует правило §6.1 буквально —
жадный поиск вопроса, который делит оставшихся кандидатов ближе всего к
пополам, с приоритетом на барьерные специальности (`TRD_PILOT`, `MED_SURG`,
`SEC_MIL`…) и без повтора оси подряд. Это не заглушка на случай отключённого
ИИ — это единственный путь скоринга, всегда: `POST /api/career-next-question`
даёт модели право выбрать один из вопросов банка (системный промпт части 6.3
дословно) или явно сказать `done`, но никогда не позволяет ей сформулировать
свой вопрос или назвать специальность. Условия остановки части 6.4 (отрыв
лидера ×1.6, ≤2 кандидата, лимит 12 вопросов на оба этапа, два вопроса подряд
без изменения тройки) — детерминированный код, не зависит от ответа модели.

**Упрощение, сделанное сознательно:** документ допускает вести этап 2
параллельно по двум полям, когда уверенность после этапа 1 ниже 0.35. Эта
версия ведёт этап 2 только по полю-лидеру — компромисс ради завершённости
остального объёма в разумный срок, а не пропущенный тест.

### Этап 3a — `lib/career/widen.ts`

«Это не про меня» — полностью детерминированное расширение, без единого
сетевого вызова. Раунд 1 — три ближайшие специализации того же поля по
локальным осям; раунд 2 — один уточняющий вопрос части 7.2 плюс явные замены
из документа (`ENG_MECH→TRD_CNC`, `MED_GP→MED_NURS`); раунд 3 — представитель
из каждого соседнего поля по матрице части 7.3, предпочтительно тот, чей
собственный текст «Что отличает» уже называет исходное поле мостом. Жёсткий
предел — три раунда (`shouldEscalateToStage3b`), дальше — передача в этап 3b,
никогда не четвёртый список.

### Этап 3b — `app/api/career-freeform/route.ts`

Системный промпт части 8.1 дословно. Модель ведёт диалог и в конце называет
1–3 id из переданного каталога — и только id: финальные строки «почему» и
«что тяжело» всегда собирает `buildResults` (тот же детерминированный код,
что и для этапов 1–2), а не текст, который написала модель. Нет офлайн-
режима: без ключа или при ошибке `POST` возвращает `unavailable: true`, и
экран честно говорит «сейчас недоступно» вместо имитации интервью.

### Безопасность и этика (часть 10)

`lib/career/safety.ts:detectCrisisSignal` — детерминированный, регэксп-
основанный детектор, проверяет каждый свободный ответ на каждом этапе
**до** того, как текст вообще уходит в скоринг или в модель. Срабатывание
немедленно останавливает интервью (`stage: "crisis"`) — без скоринга, без
следующего вопроса. Найден и исправлен через реальный прогон в браузере: первая
версия ловила только буквальное «не хочу жить» и пропускала «не хочу **больше**
жить» — живой ввод оказался естественнее, чем тестовые строки; исправлено на
паттерны, допускающие несколько слов между глаголами (`lib/career/safety.ts`,
`safety.test.ts`). Содержимое экрана поддержки — явно помеченная заглушка:
сам документ требует согласования текста со специалистом, а не выдумки
инженера. Ни одного процента совпадения нигде в модуле — структурно: ни один
шаблон, ни одна схема ответа модели не содержит поля для процента или
вероятности.

**Приватность (часть 10.7).** В LLM уходят только оси, id специализаций и
анонимизированный текст ответов — имя, школа, возраст, город, почта и телефон
не передаются структурно: в `lib/ai/career-contracts.ts` для всех трёх
вызовов просто нет таких полей.

### Голос родителя (часть 9)

Настоящая отдельная сессия, а не прокси через ответы ученика: родитель
отвечает через уже существующий аккаунт и `parent_child_links`
(`features/parent/parent-career-signal-panel.tsx`), пишет в новую таблицу
`parent_career_signal` (`supabase/migrations/0003_parent_career_signal.sql`,
RLS по образцу `parent_notes`, но с апсертом вместо лога). Никогда не
участвует в скоринге — `lib/career/parent-signal.ts` строит сравнение
(`buildParentComparison`) тем же принципом «код решает факт, модель в этом
модуле вообще не участвует», что и остальной модуль. Ученик не видит ответы
родителя внутри своего интервью ни в каком виде; сравнение доступно только в
`ParentDashboard`, и только после того, как у ученика уже есть результат.

### Роль ИИ

| Действие | Кто решает |
|---|---|
| Извлечение сдвигов по осям из свободного текста | LLM, строго по списку допустимых осей вопроса; фильтр на сервере — задняя страховка |
| Выбор следующего вопроса этапа 2 | LLM выбирает **id** вопроса из банка, никогда не формулирует свой |
| Свободное интервью этапа 3b | LLM ведёт диалог и называет **id** из каталога кандидатов |
| Оценка полей/специализаций, отбор кандидатов | Только код (`scoring.ts`, `stage2.ts`) |
| Условия остановки на каждом этапе | Только код |
| Жёсткие вето (`AVERSIONS`, Q7) | Только код, необратимо на всех этапах |
| Кризис-детектор | Только код, регэксп, работает без сети |
| Расширение результата (этап 3a) | Только код |
| Текст «почему»/«что тяжело» в итоговой карточке | Только код (`results.ts`), даже после этапа 3b |
| Сравнение с голосом родителя | Только код |

**Деградация без ИИ (часть 11.2, тест 5).** Этап 1 и весь скоринг не зависят
от модели вообще. Этап 2 без ключа отвечает тем же самым детерминированным
селектором, что обслуживает LLM-путь при сбое — не урезанная версия. Этап 3a
не использует сеть никогда. Этап 3b без ключа честно недоступен.

### Тесты

Каждая строка таблицы части 11.2 — отдельный тест в `lib/career/*.test.ts`
(не «предположительно работает» — реально прогнанный тест на каждую строку,
включая вето сквозь этап 3b и детерминизм повторного прогона). Плюс отдельные
тесты на кризис-детектор и на структурное отсутствие персональных полей в
LLM-запросах. Весь модуль прогнан живьём в браузере через реальный
Supabase-аккаунт: полные этапы 1→2, переход в этап 3a (выбор альтернативы),
перезапуск и срабатывание кризис-экрана — включая находку выше про
«не хочу больше жить».

## Аудит достоверности данных

Продукт судят на доверии: любое число, которое выглядит посчитанным, но
на самом деле подставлено или разошлось с движком, — это не мелкий баг, а
удар по всему, ради чего написан `lib/engine`. Перед этим проходом каждый
экран (Профиль, Разбор, Пути, Сравнение, План, Шаг, Найти профессию,
Кабинет родителя) был пройден заново как чужой, скептичный код-ревью: менялись
входные данные, экран открывался не по сценарию, проверялась мобильная
раскладка. Найденное и исправленное:

- **Три места честно противоречили архитектуре.** Экраны «Разбор»,
  «Источники» и начало интервью всё ещё утверждали «профиль хранится только в
  твоём браузере» — верно для билда до аккаунтов, ложно сейчас, когда профиль
  синхронизируется в Supabase. Переформулировано на то, что происходит на
  самом деле.
- **Статус срочности дублировался вручную.** `door-card.tsx` и
  `next-action-screen.tsx` заново сравнивали `days_remaining` с захардкоженным
  «14», хотя движок уже кладёт готовый ответ в `door.status`/`next.urgency`.
  Числа случайно совпадали; теперь совпадение — структурное, а не случайное.
- **Сравнение и План не показывали уровень доверия к датам и ценам**, хотя оба
  экрана их показывают. Добавлены `ConfidenceBadge` к стоимости и точке
  невозврата в сравнении и к дате шага в плане (по слабейшему факту среди
  путей, которые шаг держит — тем же принципом, каким сам движок выбирает
  уверенность одной двери).
- **У «Плана» не было понятия просрочки.** Инженерный дедлайн математически не
  может быть в прошлом для ещё открытого пути (см. доказательство в
  `lib/engine/schedule.ts` — точка невозврата это минимум всех личных
  дедлайнов цепочки, так что «путь ещё открыт» уже означает «сегодня не позже
  любого из них»). Зато собственная дата ученика («Планирую» на число, которое
  уже прошло) — это честная просрочка, и теперь она подсвечена.
- **Проверка на реальном сервере (`next start`, не только `next build`)
  вскрыла настоящий сбой:** без заполненного `.env.local` `proxy.ts` бросал
  исключение при создании Supabase-клиента на **каждой** странице из своего
  списка — включая `/start` и `/demo`, единственные экраны, доступные вообще
  без бэкенда. Это ловится только запуском настоящего сервера и обращением к
  нему — ни один тест, линт или билд этого не показывает, потому что
  `next build` не выполняет прокси-код по-настоящему. Исправлено и закреплено
  тестом (`tests/proxy.test.ts`), который проверяет ровно этот сценарий:
  пустая конфигурация не должна ронять страницу.
- Задокументированное, но не тронутое как надуманное расширение, не починка:
  `constraints.max_tuition_per_year` существует в модели, но не задаётся ни
  одним экраном (см. «Ограничения» ниже), и «стоимость за весь срок обучения»
  на сравнении невозможна честно посчитать без данных о длительности — экран
  теперь говорит это прямо, а не молчит.

Всё остальное, специально проверенное и признанное корректным без изменений:
сортировка путей по срочности (никогда по рейтингу), сводка и таймлайн на
`/doors`, настоящий диф в «Что изменилось» (не общая фраза), динамический
список «чего не знаем» на `/diagnostics`, ранжированный (не единственный)
результат «Найти профессию», и то, что числа в кабинете родителя вызывают
ровно те же функции движка, что и у ученика.

## Ограничения

- Разбор прозы берёт последний раунд подачи. Там, где вуз публикует разные
  сроки для разных категорий абитуриентов — Karolinska прямо пишет, что
  казахстанцам нужен первый раунд, — каталог назовёт более поздний. Формулировка
  вуза лежит на карточке целиком, но правило её не читает.
- Расширение каталога требует человека, который откроет сайты вузов и впишет
  источники в `data/raw/`.
- Схема и весь чек-лист из «Аутентификация и данные» прогнаны против настоящего
  Supabase-проекта, через реальный браузер (Puppeteer), а не только прочитаны
  как код — см. «Найдено живым прогоном» в том же разделе: три реальных бага
  нашлись только на этом шаге и не были видны ни в одном тесте, линте или
  билде.
- `middleware`/`proxy.ts` решает роль пользователя одним обращением к таблице
  `users` на каждый защищённый запрос — простое и корректное решение, но
  лишний round-trip по сравнению с зашитой в JWT ролью (custom access token
  hook); при заметной нагрузке это первое, что стоит оптимизировать.
- Без настроенного Supabase-проекта `proxy.ts` осознанно пропускает запрос,
  а не отвечает 500: до этой правки любая страница из его матчера — включая
  публичные `/start` и `/demo` — падала с ошибкой конструктора клиента, если
  `.env.local` ещё не заполнен. Это значит, что при пустой конфигурации
  защищённые страницы (`/doors` и остальные) технически открываются без
  редиректа на вход, но упадут на первом же обращении к Supabase внутри —
  это ожидаемо только для чистого чекаута до настройки, а не для реального
  окружения с заполненными переменными.
- Живого вызова AI-провайдера на этой машине не было: ключа нет, и путь «с
  ключом» покрыт тестами против подставного провайдера, а не реальным запросом.
- Сравнение показывает стоимость за год: длительности обучения в данных нет, и
  придумывать её ради «стоимости за весь срок» мы не стали — экран прямо
  говорит об этом под таблицей, а не молчит о разнице.
- `constraints.max_tuition_per_year` («потолок стоимости») существует в модели
  профиля и в движке (`lib/engine/profile-patch.ts`), но ни один вопрос
  интервью или экрана «Разбор» пока его не задаёт — поэтому оно никогда не
  становится ни «известным», ни «неизвестным» полем на экране. Не добавлено
  намеренно в рамках этого прохода: это расширение интервью новым вопросом, а
  не починка чего-то фейкового или сломанного.
- Точка невозврата зависит от качества данных о сроках. Там, где их не хватает,
  продукт честно отказывается считать.
